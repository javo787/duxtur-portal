# Гейт для тестов

Тест оправдан, если защищает поведение, реальную регрессию или самостоятельный контракт. Цель: уверенность, а не количество тестов.
Адаптировано из навыка test-audit проекта OpenSEO (MIT, см. NOTICE.md); режимы аудита и кампании не переносились.

## Перед добавлением теста ответь на четыре вопроса

Нет ответа на любой: теста пока не добавлять.

1. Какое наблюдаемое поведение или контракт он защищает?
2. Какая реальная регрессия его уронит?
3. Почему существующие тесты её не ловят? У каждого контракта один главный владелец на самой сильной границе. Дополняй таблицу кейсов рядом стоящего теста, а не копируй его.
4. Нужен ли для теста экспорт, флаг или обёртка, которых не требует ни один боевой вызов? Если да, тестируй на настоящей границе. Перед этим найди все вызовы по всему репозиторию, включая `scripts/`.

Регрессионный тест на баг обязан падать на коде до исправления и проходить после. Тест, который не падал, доказывает мок, а не исправление.

## Мусорные шаблоны (тест отклоняется)

- Тест без проверок, «для покрытия».
- Сравнение значения с самим собой; ожидаемое значение получено тем же кодом, который тестируется.
- Проверка исходного текста файла по строке или импорту.
- Один и тот же контракт вызван дважды.
- Мок реализует то поведение, которое проверяется, или один и тот же мок изображает разные API.
- Негативный кейс проходит по посторонней причине (отказ другого условия, а не проверяемого).
- Название или данные обещают больше, чем проверяет вход.
- Данные теста длиннее проверок, которые их читают.
- `vi.resetModules()` или динамический `import()` в каждом тесте без комментария, какое состояние модуля сбрасывается.
- Повторная проверка чужой библиотеки через тестируемый модуль.

## Что сохранять всегда (контракты Duxtur)

- Пороги индексации, решение «индексировать или нет» и JSON-LD без выдуманных рейтингов: `src/lib/clinic-seo.test.ts`.
- Состав sitemap (импорт попадает только с собственным текстом, фасеты только с достаточным числом клиник, нет закрытых страниц): `src/lib/sitemap-entries.test.ts`.
- Согласованность sitemap и robots.txt: `src/lib/seo-consistency.test.ts`, `src/app/robots.test.ts`.
- Главный хост и canonical: `src/lib/canonical-host.test.ts`, `doctor-seo.test.ts`, `blog-seo.test.ts`.
- Авторизация и права доступа: `src/lib/authGuards.test.ts`.
- Проверка разметки: `npm run test:seo`.

Статичный или медленный тест не повод его удалять. Тест, повторяющий реализацию, может оказаться единственным независимым контрактом: докажи обратное, прежде чем убирать.

## Практика

- Чистую логику выноси в `src/lib` и тестируй рядом: `имя.ts` и `имя.test.ts`.
- Данные: табличные кейсы вместо копий почти одинаковых тестов.
- Тест, падающий на базовой ветке: возможная ошибка продукта. Воспроизведи и чини владельца, а не удаляй тест.
- Перед коммитом: `npm run typecheck`, eslint по изменённым файлам, `npm test`. Запуск `next build` в песочнице невозможен.
